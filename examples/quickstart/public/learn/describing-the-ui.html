Describing the UI

Phem is a library for rendering user interfaces. A UI is built from small units like buttons, text and images. Phem lets you combine them into reusable, nestable components.

Importing and exporting components#

You can declare many components in one file. When an app grows, put the reusable components in their own files and compose them in a page. React uses export and import for this. Phem uses PHP namespaces:

  • Put the shared components in src/Components/, in the namespace App\Components. They have no #[Page] attribute, so they are not pages.
  • In the page file, import a function component with use function App\Components\{Layout, Profile};.
  • Import a class component with use App\Components\LikeButton;.
  • A component in the same namespace needs no import. Profile uses <LikeButton /> without an import.

The page Gallery.phpm below uses components from three other files. Layout is the page shell: it gets the page content as children and a named slot <Layout:footer>. Each LikeButton keeps its own state. Click the tabs to see each file:

The compiler finds the component of each tag at build time, with the PHP rules: first a use function import, then a use import of a class, then the current namespace. It checks the props across files too: an unknown component or prop is an error (E010, E011), with the .phpm line of the tag.

Reading data from a database#

In Gallery.phpm, the scientists are a PHP array, and each like is browser state: a reload clears it. In a real app, the data comes from a database. Components render on the server, so a component can read the database directly. You do not need an API between them.

The page DurableGallery.phpm below is the same gallery, with the data in SQLite. It uses Doctrine ORM through DoctrineBundle:

  • src/Model/Scientist.php is a Doctrine entity: one row of the scientist table.
  • src/Repository/ScientistRepository.php is the data layer: a ServiceEntityRepository of the entity. It only reads and adds rows. It does not make the database: the Docker entrypoint makes var/data/gallery.sqlite and loads the fixtures of src/DataFixtures/.
  • The page is a class component. The container injects the repository in its constructor, and the page reads the entities with $this->scientists->all() in mount(). render() does not call the repository: it only shows the entities that mount() read. The page has no #[State], so mount() runs each time that the page renders. It reuses Layout and Avatar from the files above.
  • The handlers write to the database. LikeCounter gets the Scientist entity as a prop and increments its likes. AddScientist reads a Symfony form from $e->request and calls add() on the repository. Each handler runs in a Doctrine transaction: Phem flushes and commits when the handler returns, so the handlers do not call flush().
  • After a handler, the server renders the page again. It reads the new rows and morphs only the components that changed.

Click a like button, add a scientist, then click Reset or open the page in another browser. The data stays. Submit an empty form: the validation errors of the form show in the render after the handler. They are not state, so they go away on the next event.

The key on LikeCounter is the row id. The server finds the handler of an event by the position of the component in the tree. With a key, a click goes to the correct row, also when the rows change between the page load and the click (for example, when a row is deleted).

One connection for each worker

FrankenPHP runs the application in worker mode: each worker boots the kernel once and handles many requests. Doctrine opens the connection once in each worker and keeps it. The kernel resets the services between requests, and the reset clears the entity manager, so a request never gets the entities of an earlier request. A worker handles one request at a time, so a slow query blocks only its worker. SQLite on a local file is fast. For a remote database, keep the queries short.
