Learn Mamu

Quick Start

Welcome to the Mamu documentation. This page is a short tour of the Mamu ideas that you will use every day. If you know React, most of it will look familiar: Mamu is React for PHP and Twig.

You will learn

  • How to create and nest components
  • How to add markup and styles
  • How to display data
  • How to render conditions and lists
  • How to respond to events and update the screen
  • How to share data between components

Creating and nesting components#

A Mamu app is made of components. A component is a piece of the UI with its own logic and look. A component can be as small as a button or as large as a full page.

A Mamu component is a PHP function that returns markup. You write it in a .phpm file:

function MyButton()
{
    return (
        <button>I'm a button</button>
    );
}

Now that you declared MyButton, you can nest it into another component:

Look at <MyButton />: it starts with a capital letter. That is how you know it is a Mamu component. Component names always start with a capital letter. HTML tags are always lowercase.

The #[Page] attribute makes a class a page. React uses export default for the page component. In Mamu, #[Page] (a Symfony route) exposes the class at a URL, as #[Route] does for a Symfony controller, and the code stays valid PHP. A page class is a component with no #[Component], and it renders its content in the <Document> of your application. The class MyApp above has #[Page('/examples/MyButton')], so it is the page /examples/MyButton. To find the component of a tag, the compiler uses the PHP rules: first a use function import, then a use import of a class, then the current namespace.

Writing markup with Mamu#

The markup above is a markup literal. React uses JSX for this. Mamu uses the same idea in PHP: a markup literal is a PHP expression, and its value is a Mamu\Html object. The mamuc compiler turns each markup literal into a Twig template at build time. Nothing is parsed when a request comes in.

Markup is stricter than HTML. You must close all tags, for example <br />. A component also cannot return more than one root tag. Wrap the tags in a shared parent, such as a <div> or an empty fragment <>...</>:

function AboutPage()
{
    return (
        <>
            <h1>About</h1>
            <p>Hello there.<br />How do you do?</p>
        </>
    );
}

Note

A markup literal can start anywhere a PHP expression can start: after return, (, =, ,, =>, ?, :, ??, [ and echo.

Adding styles#

To give a tag a CSS class, use className. It works the same way as the HTML class attribute. (You can also write class. The two names are aliases, like htmlFor and for.)

<img className="avatar" />

Then write the CSS rules in a separate CSS file:

assets/styles/app.css
/* In your CSS */
.avatar {
    border-radius: 50%;
}

Import the CSS file in assets/app.js, the JavaScript of the pages. AssetMapper links it on each page:

assets/app.js
import './bootstrap.js';
import './styles/app.css';

Your application owns the HTML document of the pages: a component, as the others. It prints the page content in a <Root>, the root element that the events update, and {{ importmap('app') }} loads the assets:

src/Components/Document.phpm
use Mamu\{Html, Root};

function Document(?Html $title = null, ?Html $children = null)
{
    return (
        <html lang="en">
            <head>
                <title>{{ title ?? 'My app' }}</title>
                {{ importmap('app') }}
            </head>
            <body><Root>{{ children }}</Root></body>
        </html>
    );
}

Each page renders its content in it. A page gives its title with the title slot:

<Document>
    <Document:title>{{ scientist.name }}</Document:title>
    <h1>{{ scientist.name }}</h1>
</Document>

When the class depends on a value, give className a list. Mamu joins the items with spaces and drops the empty items:

<li className={{ ['item', isActive ? 'active' : ''] }}>
    {{ item.title }}
</li>

Displaying data#

In JSX, curly braces like {user.name} take you back into JavaScript. In Mamu, the text and the attribute values of markup are Twig. Use the Twig syntax {{ }} to print a value. The Twig variables are the PHP variables of the function: $user is user in Twig, and {{ user.name }} prints the name key of the array.

return (
    <h1>
        {{ user.name }}
    </h1>
);

Twig escapes the value when it prints it, so text from users is safe. The only exception is markup: an Html value prints as HTML.

An attribute can also take a value from PHP. Write src={{ user.imageUrl }} to pass the value of the variable. A quoted value such as src="/img/avatar.svg" is a plain string. A quoted value can also contain Twig, for example alt="Photo of {{ user.name }}":

return (
    <img
        className="avatar"
        src={{ user.imageUrl }}
        alt="Photo of {{ user.name }}"
    />
);

Twig expressions can be more complex too. You can join strings with the ~ operator, and use all the Twig filters and tests:

In this example, style={{ {width: user.imageSize} }} is not a special syntax. It is a Twig hash inside the {{ }} braces. Mamu changes camelCase keys to kebab-case and adds px to numbers.

Compute first, then return

Do not put PHP code in markup. Compute the values in PHP before the return, then print them with Twig. This keeps the template simple, and the compiler can make it into fast Twig code.

Conditional rendering#

Mamu has no special syntax for conditions. Use the same code that you use in plain PHP. For example, use an if statement to select the markup. A markup literal is a value, so you can keep it in a variable:

if ($isLoggedIn) {
    $content = <AdminPanel />;
} else {
    $content = <LoginForm />;
}

return (
    <div>
        {{ content }}
    </div>
);

For a shorter form, use a Twig expression inside the markup. The Twig ternary operator and the and operator take markup too. The Twig {% if %} tag also works:

{# The ternary operator #}
<div>{{ isLoggedIn ? <AdminPanel /> : <LoginForm /> }}</div>

{# Like && in JSX: render the panel or nothing #}
<div>{{ isLoggedIn and <AdminPanel /> }}</div>

{# A Twig if tag #}
<div>{% if isLoggedIn %}<AdminPanel />{% else %}<LoginForm />{% endif %}</div>

Rendering lists#

To render a list of items, use the Twig {% for %} tag or the PHP array_map() function. For example, you have an array of products:

$products = [
    ['title' => 'Cabbage', 'id' => 1],
    ['title' => 'Garlic', 'id' => 2],
    ['title' => 'Apple', 'id' => 3],
];

Loop over the array in the markup with a {% for %} tag:

return (
    <ul>
        {% for product in products %}
            <li key={{ product.id }}>{{ product.title }}</li>
        {% endfor %}
    </ul>
);

Or do the same as map() in React. An array of markup prints as a list:

$listItems = array_map(
    fn($product) => <li key={{ product.id }}>{{ product.title }}</li>,
    $products,
);

return <ul>{{ listItems }}</ul>;

Each <li> has a key attribute. For each item in a list, give a string or a number that identifies it among its siblings, for example key={{ product.id }}. Usually a key comes from your data, such as a database ID. Mamu uses the keys to know what changed when it updates the page.

Responding to events#

You respond to events with event handler functions. Declare the handler in the component, then pass it to an event attribute:

function MyButton()
{
    $handleClick = fn() => error_log('You clicked me!');

    return (
        <button onClick={{ handleClick }}>
            Click me
        </button>
    );
}

Look at onClick={{ handleClick }}: there are no parentheses at the end. Do not call the handler function, as in onClick={{ handleClick() }}. Only pass it down. Mamu calls the handler when the user clicks the button.

Mamu supports these events:

  • onClick
  • onDoubleClick
  • onChange
  • onInput
  • onSubmit
  • onKeyDown
  • onKeyUp
  • onFocus
  • onBlur

The handler receives a Mamu\Event object. It has $e->value, $e->checked, $e->key, $e->form (an array, for onSubmit), and $e->request (the Symfony request of the event, for Symfony forms). As in React, onChange on a text input fires on each key. Type in the box:

Where does the handler run?

This is the largest difference from React. A Mamu event handler is PHP, so it runs on the server. When you click, the browser sends the event and the state of the component to the server. The server runs the handler, renders the component again, and sends back Turbo Streams. Turbo morphs only the parts of the page that changed. You do not write any JavaScript for this. In the MyButton code above, error_log() writes to the server log, not to the browser console.

Updating the screen#

Often, you want your component to "remember" some information and show it. For example, you want to count the number of times that a button is clicked. To do this, add state to your component.

A component with state is a class. Mark it with #[Component], and mark each state property with #[State]:

use Mamu\Attribute\{Component, State};

#[Component]
final class Counter
{
    #[State] public int $count = 0;
    // ...
}

The first time the button shows, $count is 0, its default value. To change the state, write a method that changes the property, and pass the method as the event handler. In the markup of a class, a name is first a local variable, then a property ($this->count), then a method ($this->handleClick(...)):

    public function handleClick(): void
    {
        ++$this->count;
    }

    public function render()
    {
        return (
            <button onClick={{ handleClick }}>
                Clicked {{ count }} times
            </button>
        );
    }

After the handler runs, Mamu calls render() again, and $count is 1. Then it is 2, and so on.

If you render the same component more than one time, each one gets its own state. Click each button separately:

Where does the state live?

In React, the state lives in the memory of the browser tab. In Mamu, the state lives in the browser too, but in a different form: the mamu Stimulus controller keeps it in the page, and the server signs it. Each event sends the state to the server, and the server sends back the new state with the new markup. The server keeps nothing between requests. For this reason, state values must be JSON values: scalars and arrays. Click Reset on a sandbox: the page loads again, and the state goes back to its first value.

Services and initialization#

A Mamu application is a Symfony application, and each class component is a service. The container makes a new object for each component on the page, so the constructor gets the services that the component needs (autowiring), as in a Symfony controller:

#[Component]
#[Transactional]
final class AddScientist
{
    public string $label = 'Add';  // a prop

    public function __construct(private readonly ScientistRepository $scientists)
    {
    }

    public function add(Event $e): void
    {
        $this->scientists->add(new Scientist($e->form['name'], $e->form['profession']));
    }

    public function render()
    {
        return (
            <form onSubmit={{ add }}>
                <input name="name" />
                <input name="profession" />
                <button type="submit">{{ label }}</button>
            </form>
        );
    }
}

The parts of a class component:

  • The constructor gets the services. Its parameters are never props.
  • Public properties are the props. A property without a default value is a required prop.
  • #[State] properties are the state. The browser keeps them, so they must be JSON values.
  • mount() (optional) sets the first state. It runs after the props are set, when the component has no state yet: on its first render. For example, $this->items = $this->repository->latest($this->limit);.
  • Methods are event handlers. A handler can change the state and call the services.
  • render() returns markup.
  • #[Transactional] (optional) runs each handler in a Doctrine ORM transaction. When the handler returns, Mamu flushes and commits. Thus the repository only calls persist(), and the handler does not call flush().

A component without state does not need a class. A function that returns markup is a component too, and its parameters are its props. If its body is only return <markup>;, it compiles to a plain Twig template, with no PHP call. Here is a page that is a class with a prop and state:

What about Hooks?

React keeps state in Hooks such as useState. A Hook needs a global "current component", so Mamu uses objects instead: a #[State] property for useState, a method for an event handler, mount() for the first state, and constructor injection for shared things that React puts in a context. If a file calls useState or another React Hook name from Mamu, the mamuc compiler reports the error E020.

Sharing data between components#

In the previous example, each Counter had its own independent $count. When you clicked one button, only the $count of that button changed. But often you need components to share data and always update together.

To make both buttons show the same count and update together, move the state from the buttons "upward" to the nearest component that contains all of them. Then pass the state down to each button. This is called lifting state up.

First, move the state up from the button into the parent component. Then pass the state down from the parent, together with the click handler. You pass information down as props, with the same Twig syntax as attributes:

#[Page('/examples/CounterTogether')]
final class CounterTogether
{
    #[State] public int $count = 0;

    public function handleClick(): void
    {
        ++$this->count;
    }

    public function render()
    {
        return (
            <Document>
                <h1>Counters that update together</h1>
                <CountButton count={{ count }} onClick={{ handleClick }} />
                <CountButton count={{ count }} onClick={{ handleClick }} />
            </Document>
        );
    }
}

In Mamu, props are the named parameters of the function. Change the button to read the props that its parent passes:

function CountButton(int $count, Closure $onClick)
{
    return (
        <button onClick={{ onClick }}>
            Clicked {{ count }} times
        </button>
    );
}

When you click a button, the onClick handler runs. It is the handleClick() method of the parent, so it changes the state of the parent. The parent renders again with the new $count and passes it to both buttons. A prop with an unknown name is an error, and PHP checks the types of the parameters as usual.

A generic component cannot know all the attributes that its callers want to give. Add a variadic parameter: it collects the props that no other parameter takes, as ...rest does in React. Then spread them on the element with {{ ...props }}. The handlers go through too, so onClick does not need its own parameter:

function CountButton(int $count, mixed ...$props)
{
    return (
        <button type="button" {{ ...props }}>
            Clicked {{ count }} times
        </button>
    );
}

As in JSX, the order counts: a later value replaces an earlier one. Here type="button" is a default, and a caller can replace it with type="submit".

Children and slots

A component can also receive markup. The content between the tags goes to the ?Html $children parameter: <Card>...</Card>. A named slot, such as <Card:footer>...</Card:footer>, goes to the ?Html $footer parameter.
